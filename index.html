Cuaderno de Claude Code

Apuntes de una formación agéntica

Aprendiendo a dirigir agentes, no solo a chatear con uno

Estos son los apuntes de una formación completa sobre los flujos agénticos de Claude Code — desde la configuración base hasta orquestar equipos de agentes en producción. Cada sección viene de ejemplos construidos y probados contra un proyecto real, no de teoría suelta.

Escrito por Juanda, con Claude como profesor. Pensado para cualquiera que quiera pasar de usar Claude Code de forma básica a diseñar sistemas agénticos con control real sobre coste, permisos y ejecución.

01Fundamentos

CLAUDE.md

Es el archivo que Claude Code carga en cada sesión — el equivalente a explicarle el proyecto a un compañero nuevo, pero una sola vez. Puede vivir en dos sitios, ambos válidos: ./CLAUDE.md en la raíz (el más común, junto al README) o ./.claude/CLAUDE.md. Se genera con /init y luego se pule a mano.

IncluirExcluir
Comandos que Claude no puede adivinar (test individual, build)Cosas deducibles leyendo el código
Convenciones de estilo que difieren del estándarConvenciones estándar del lenguaje
Reglas de git/PR del equipoDocumentación larga de API (mejor un enlace)

Regla de oro

Para cada línea: "si la quito, ¿Claude se equivocaría?" Si no, sobra. Objetivo: menos de 200 líneas — un archivo largo hace que Claude ignore reglas porque se pierden entre el ruido.

Si el proyecto ya usa AGENTS.md (el estándar cruzado entre herramientas — Codex, Cursor, Copilot), Claude Code no lo lee de forma nativa. Se soluciona importándolo desde CLAUDE.md:

@AGENTS.md

## Solo para Claude Code
Usa plan mode para cambios en src/billing/.

En monorepos, Claude busca CLAUDE.md subiendo por el árbol de directorios — puedes tener uno general en la raíz y otros más específicos en packages/api/. También existe ~/.claude/CLAUDE.md para preferencias tuyas que aplican a todos tus proyectos.

Permisos y modos

Desde hace poco, el modo por defecto en Pro/Max/Team ya no es "preguntar siempre" — es auto mode: un clasificador revisa las acciones y solo interrumpe cuando algo parece realmente arriesgado.

ModoComportamiento
planSolo lectura — explora sin tocar nada
acceptEditsAuto-acepta ediciones y comandos comunes
autoUn clasificador decide (por defecto en Pro/Max/Team)
dontAskDeniega lo que no esté explícitamente permitido
bypassPermissionsSin comprobaciones

/permissions abre un panel con las reglas activas (alias /allowed-tools). Cada regla es allow, ask o deny, con formato Herramienta(patrón) — por ejemplo Bash(git push:*) o Task(nombre-de-agente). Se evalúan en orden deny → ask → allow, y gana la primera coincidencia, sin importar cuál sea más específica.

Viven en tres niveles: ~/.claude/settings.json (tú, todos tus proyectos), .claude/settings.json (equipo, va a git), .claude/settings.local.json (tú, este proyecto — normalmente en .gitignore).

MCP — conectar herramientas externas

MCP le da a Claude herramientas ejecutables que hablan con servicios reales (Notion, Postman, una base de datos), no solo archivos. Es una conexión viva, distinta de cualquier archivo de configuración.

claude mcp add --transport http nombre https://url-del-servidor
claude mcp add --transport stdio nombre --env KEY=valor -- npx -y paquete
ScopeVive enAlcance
local (default)Estado de usuarioSolo tú, este proyecto
project.mcp.json, va a gitTodo el equipo, este proyecto
user~/.claude.jsonTú, todos tus proyectos

Detalle importante

Claude Code sincroniza automáticamente los conectores que ya tienes activos en claude.ai (Notion, Postman, Figma...). Es todo-o-nada a nivel de cuenta: se registran en todos tus proyectos, sin scoping fino por proyecto todavía.

Un subagente solo ve los servidores MCP listados explícitamente en su campo mcpServers — así puedes evitar que un subagente cargue conectores que no necesita, aunque estén sincronizados globalmente.

02El bucle de trabajo

Dale a Claude una forma de verificarse

Sin un check ejecutable, "parece terminado" es la única señal que existe. Con un check (tests, build, captura comparada con un diseño), el bucle se cierra solo: Claude implementa, corre el check, lee el resultado, itera.

Nivel de autonomíaMecanismo
Un mensajePide correr el check en la misma instrucción
Toda la sesión/goal — condición de éxito evaluada tras cada turno
Puerta deterministaHook Stop que bloquea hasta que el check pase
Segunda opiniónSubagente en contexto limpio que intenta refutar el resultado

Explorar → Planificar → Codificar

Plan mode es un modo de permisos, no un subagente aparte: restringe la sesión a herramientas de solo lectura (Read, Grep, Glob, WebFetch, WebSearch, TodoWrite) y bloquea Edit/Write/la mayoría de Bash.

  • Entrar: Shift+Tab (cicla modos), /plan, claude --permission-mode plan (funciona headless), o defaultMode: "plan" en settings.json
  • Salir: Claude llama a la herramienta ExitPlanMode, presenta el plan, exige confirmación explícita

Matices honestos

El límite lo aplica una instrucción de sistema más el sistema de permisos — no es un sandbox real. Plan mode bloquea escrituras, no lecturas: puede seguir leyendo archivos sensibles. Y las transiciones de entrada/salida de plan mode todavía no son visibles para el sistema de hooks.

Gestión de contexto

La ventana por defecto son 200K tokens, y ya hay ocupación antes de escribir nada:

ComponenteCoste típico
System prompt + herramientas base~20.000 (fijo)
Esquemas de servidores MCP900–51.000 (según cuántos tengas)
CLAUDE.md300–2.000 — sobrevive a la compactación

El auto-compact se dispara al acercarse a la capacidad (el umbral exacto varía según versión, aproximadamente 75-95%), en dos fases: primero se limpian resultados de herramientas (lecturas de archivo, greps, salidas de bash — suele ser 60-80% del consumo), luego se resume la conversación restante. Se pierde el detalle fino (rutas exactas, texto de errores); sobrevive lo estructural (decisiones, patrones, CLAUDE.md).

  • /clear — entre tareas no relacionadas, evita forzar una compactación en mal momento
  • /compact <foco> — compactación manual con instrucciones de qué preservar
  • /rewind — restaura código, conversación o ambos a un punto anterior

03Subagentes

Un subagente corre en su propia ventana de contexto, con su propio system prompt y su propio conjunto de herramientas. Vive en .claude/agents/nombre.md (proyecto, va a git) o ~/.claude/agents/ (usuario, todos tus proyectos).

---
name: security-auditor
description: Auditor de seguridad senior. Revisa cambios en busca de
  vulnerabilidades. Invócalo explícitamente con @security-auditor.
tools: Read, Grep, Glob, Bash(git diff:*), Bash(git log:*)
model: inherit
memory: project
---

Eres un auditor de seguridad senior. Piensas como un atacante...
CampoQué hace
toolsLista exacta permitida — cualquier otra herramienta falla estructuralmente, no por criterio del agente
modelinherit, o fija haiku para tareas simples y ahorrar, opus para rigor
permissionModeModo de permisos propio, independiente del de la sesión principal
maxTurnsLímite duro de turnos — evita que se quede corriendo indefinidamente
isolation: worktreeEdita en su propia copia aislada del repo
background: trueCorre en segundo plano sin bloquear la sesión
memory: projectRecuerda entre sesiones (en .claude/agent-memory/)
mcpServersSolo los servidores MCP listados aquí — no hereda los de la sesión

Proactivo vs. manual

La palabra "proactively" en la description es la señal que hace que Claude lo dispare solo. Quitarla no es un bloqueo técnico absoluto, pero reduce mucho la probabilidad — para una garantía dura, combínalo con una regla ask en permisos sobre Task(nombre-del-agente).

Los que ya tienes gratis

Lo que un subagente ve — y no ve

Solo su propio system prompt, el prompt de la tarea, info del entorno, y los skills/MCP que liste explícitamente. No hereda tu historial de conversación ni lo que tu sesión principal tiene cargado.

04Hooks

Donde CLAUDE.md sugiere, un hook garantiza: un script que se ejecuta sí o sí en un punto del ciclo de vida, fuera del control del modelo. Se configuran en settings.json o interactivamente con /hooks.

El hook recibe JSON por stdin y decide con su código de salida: 0 = adelante, 2 = bloquea y devuelve el motivo a Claude por stderr, otro código = advertencia no bloqueante. Eventos núcleo: PreToolUse, PostToolUse, Stop, SessionStart, UserPromptSubmit, SubagentStop (se dispara cuando termina un subagente concreto).

Ejemplo real: cerrar el círculo de una auditoría

Dos hooks trabajando juntos — cuando security-auditor termina, marca el commit como auditado; al intentar git push, se comprueba esa marca:

{
  "hooks": {
    "SubagentStop": [{ "hooks": [{ "type": "command",
      "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/mark-audit-passed.sh" }] }],
    "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command",
      "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/require-audit-before-push.sh" }] }]
  }
}

Prueba antes de confiar

Hay reportes documentados de PreToolUse con exit 2 que no bloquearon git push en ciertas versiones. Antes de depender de esto para algo crítico, verifica tú mismo que de verdad se detiene.

05Skills

Una carpeta con SKILL.md (frontmatter + instrucciones) que Claude carga por su cuenta cuando la tarea coincide con la description — sin invocación manual necesaria. La clave es el coste: al arrancar, solo se cargan nombre y descripción de cada skill (~80 tokens), el cuerpo completo se queda en disco hasta que se dispara de verdad.

Estructura recomendada para skills grandes: SKILL.md (delgado, bajo 500 líneas) + scripts/ (código ejecutable) + references/ (docs cargados solo si hace falta) + assets/ (plantillas). Vive en .claude/skills/nombre/.

---
name: nuevo-endpoint-api
description: Checklist para añadir un endpoint nuevo a la API.
---

# Añadir un nuevo endpoint
1. Define el contrato antes de escribir código
2. Sigue el patrón de un endpoint existente similar
3. Valida con @api-tester antes de terminar

06Plugins

Empaquetan subagentes, hooks, skills y declaraciones MCP en una unidad instalable con un comando, en vez de que cada persona copie archivos sueltos. Dos manifiestos con trabajos distintos: marketplace.json es el catálogo, plugin.json es la identidad del plugin.

mi-marketplace/
├── .claude-plugin/marketplace.json
└── mi-plugin/
    ├── .claude-plugin/plugin.json
    ├── agents/       (auto-descubierto)
    ├── hooks/hooks.json
    └── scripts/
/plugin marketplace add ./mi-marketplace
/plugin install mi-plugin@mi-marketplace

Los componentes van en la raíz del plugin, no dentro de .claude-plugin/ — Claude Code escanea carpetas con nombre reservado (agents/, hooks/, skills/, commands/) automáticamente. Dentro de hooks.json, usa ${CLAUDE_PLUGIN_ROOT} en vez de $CLAUDE_PROJECT_DIR — el plugin puede instalarse en cualquier ruta.

Lo que un plugin NO empaqueta

Una conexión MCP autenticada (cada persona necesita la suya propia) ni las reglas de settings.json de quien lo instala — eso sigue siendo local a cada persona/proyecto.

07Paralelismo

Git worktrees

Varias carpetas de trabajo, cada una en una rama distinta, todas leyendo del mismo historial compartido — sin clonar el repo. claude --worktree nombre a nivel de sesión, o isolation: worktree en un subagente para lo mismo automáticamente.

git worktree add ../mi-proyecto-bugfix bugfix-branch
git worktree list
git worktree remove ../mi-proyecto-bugfix

Gotcha real

Un worktree nuevo solo contiene archivos ya trackeados por git. .env, node_modules, .venv nunca formaron parte de ese historial — no es un bug, es la consecuencia de cómo funciona el mecanismo.

Agent teams

Un agente líder decompone la tarea; los teammates trabajan en contextos aislados y se mensajean directamente entre sí — a diferencia de un subagente, que solo devuelve resultado a quien lo llamó. Añaden bloqueo de archivos para evitar sobrescrituras concurrentes. No hay comando especial: se describe en lenguaje natural.

Crea un equipo para revisar el PR #142. Tres revisores:
seguridad, rendimiento y cobertura de tests. Que reporten
de forma independiente.

08Automatización en producción

GitHub Actions

/install-github-app instala la GitHub App, añade la API key como secret, coloca el workflow. Tres modos automáticos: Interactivo (mención @claude), Automation (prompt explícito), Review (se dispara en cada PR, comenta directamente).

Routines

Un prompt guardado + los repos/conectores a los que accede, corriendo en la nube de Anthropic — no en tu máquina. Sin estado entre ejecuciones. Tres triggers combinables: schedule (mínimo 1 hora, tu zona horaria), API (endpoint HTTP propio por rutina), GitHub (eventos del repo, requiere instalar la GitHub App aparte).

/goal

Define una condición de finalización; tras cada turno, un modelo distinto y más ligero (Haiku por defecto) evalúa si se cumple — no el mismo Claude que hizo el trabajo, para evitar que sea juez y parte. Requiere v2.1.139+ y el diálogo de confianza del workspace aceptado.

/goal migra este módulo hasta que todos los tests pasen --max-iterations 20

09Coste y economía de tokens

  • Los subagentes no tienen descuento — consumen del mismo pool que tu sesión interactiva. El coste escala linealmente con la concurrencia, no con el mero hecho de usarlos: un subagente puntual suele ser más barato que hacerlo inline; varios en paralelo drenan la cuota proporcionalmente.
  • Agent teams puede llegar a consumir ~7x una sesión normal en plan mode — varias instancias completas corriendo a la vez, en modelos distintos.
  • Tu plan tiene dos capas: una ventana rodante de 5 horas (no se banca si no la usas) y un tope semanal acumulado. Las routines consumen del mismo pool que el uso interactivo — según la documentación oficial — aunque hay reportes de casos donde la facturación no siguió esa regla correctamente. Vale la pena vigilar el dashboard de coste las primeras veces.
